## 1. Classic semantic file systems lineage — and what killed them

**Gifford et al., "Semantic File Systems" (SOSP 1991)** is the root of the whole tree: file-type-specific *transducers* auto-extract attributes; *virtual directories* whose names are interpreted as queries (`ls /sfs/owner:/smith/text:/resume`) provide associative access while staying NFS-compatible ([paper PDF](https://web.mit.edu/6.826/archive/S97/13-Gifford-Semantic-file-systems-paper.pdf), [ACM DL](https://dl.acm.org/doi/10.1145/121132.121138)). Two ideas survive intact in 2026: transducers (Indaleko uses the term verbatim) and query-as-path virtual views.

**Placeless Documents / Presto (Xerox PARC, ~1999-2001)** replaced hierarchy with user-level key/value *properties* as the uniform organizing mechanism ([Presto UIST'99](https://sites.cc.gatech.edu/home/keith/pubs/presto-uist99.pdf), [TOCHI paper](https://faculty.cc.gatech.edu/~keith/pubs/tochi-presto.pdf)). It ended around 2000-2001 as patents, not product; its ideas leaked into Gmail labels, Spotlight, and macOS tags.

**Lifestreams (Freeman & Gelernter, Yale, 1996-97)** replaced hierarchy with a single time-ordered stream ([project page](http://www.cs.yale.edu/homes/freeman/lifestreams.html), [SIGMOD Record](https://dl.acm.org/doi/10.1145/381854.381893)). Commercialized as Scopeware (2001), which folded; the patents ended in litigation (Mirror Worlds v. Apple) and were sold to Network-1 in 2013. Conceptually it *won* — every social timeline is a lifestream — but not as a file store.

**TagFS-family systems** are several unrelated projects (a 2006 WebDAV semantic-web TagFS, an [MIT 6.033 design exercise](https://web.mit.edu/6.033/2011/wwwdocs/writing-samples/sbezek_dp1.pdf), FUSE hobby projects, [surviving tools like TMSU/tagsistant](https://alternativeto.net/software/tagfs)); nearly all dormant. Nayuki's essay ["Designing better file organization around tags, not hierarchies"](https://www.nayuki.io/page/designing-better-file-organization-around-tags-not-hierarchies) is the best modern statement of the design space.

**What killed them, distilled from the record:**
1. **The hierarchy is baked into the OS API surface** — semantic FSes are inevitably databases bolted onto a real FS; every app still speaks paths ([OBJS survey](http://www.objs.com/survey/OFSExt.htm), [fsgeek commentary](https://fsgeek.ca/my-research/semantic-file-systems/)).
2. **Tagging effort exceeds tagging payoff** — users given both folders and tags prefer folders and rarely add more than one tag per item (see §7).
3. **No incremental adoption path** — Presto/Lifestreams demanded paradigm switch, not overlay.
4. **The winning ideas were absorbed piecemeal** (desktop search, labels, smart folders) which removed the pressure to replace the FS itself.

## 2. Modern LLM/embedding-era work (2023-2026)

- **LSFS — "From Commands to Prompts: LLM-based Semantic File System for AIOS" (ICLR 2025, arXiv:2410.11843)** is the load-bearing modern revival: semantic indexes over a vector DB at the micro level, semantic syscalls (CRUD, group-by, join, semantic rollback) at the macro level, sitting on the AIOS agent-OS. Claims +15% retrieval accuracy at 2.1× speed vs. traditional FS navigation ([arXiv](https://arxiv.org/abs/2410.11843), [code](https://github.com/agiresearch/AIOS-LSFS)). Directly relevant as prior art for "store as semantic API, not tree."
- **Indaleko: The Unified Personal Index** (W. A. Mason / "fsgeek," UBC PhD thesis, arXiv:2602.20507, Feb 2026) — arguably the closest thing to this objective in the literature: a unified graph index over 31M files / 160TB / 8 storage platforms, combining storage metadata + Gifford-style semantic transducers + *activity context* (temporal/spatial/episodic cues), enabling "photos near the conference venue last spring" with sub-second response ([arXiv](https://arxiv.org/abs/2602.20507), [GitHub ubc-systopia/Indaleko](https://github.com/ubc-systopia/Indaleko)). Its core thesis — align retrieval with episodic human memory, not keywords — is the right corrective to pure-embedding designs.
- **LlamaFS (iyaja/llama-fs, 2024)** — the viral "self-organizing file system": batch reorganization + a watch daemon that learns your renaming behavior from recent edits; local mode via Ollama ([GitHub](https://github.com/iyaja/llama-fs), [HN thread](https://news.ycombinator.com/item?id=40484512)). The HN discussion is a compact catalog of user objections (why intercept the FS at all; want review-before-move; want rule "binning"). Mostly abandoned hackathon-ware — instructive as both existence proof and cautionary tale.
- **Filesystem-Based Memory for LLM Agents (arXiv:2607.26637, July 2026)** — agents organizing a memory filesystem; key negative result: *organization erodes for all but the strongest management agent, and no measured agent converts organization itself into better answers* ([arXiv](https://arxiv.org/abs/2607.26637)). This is a direct empirical warning for the "LLM continuously reorganizes your store" loop.
- **Workspace-Bench 1.0 (arXiv:2605.03596)** — benchmark generating realistic noisy directory hierarchies conditioned on user profiles; useful eval substrate ([arXiv HTML](https://arxiv.org/html/2605.03596v1)).
- **Embedding-based personal capture**: Rewind (macOS, local encrypted screen/audio timeline) and **Windows Recall** — Microsoft's phrase is literally "your personal semantic index, built and stored entirely on your device": OCR + semantic indexing + on-disk vector DB on an NPU ([Wikipedia](https://en.wikipedia.org/wiki/Windows_Recall), [Beaumont's security analysis](https://doublepulsar.com/microsoft-recall-on-copilot-pc-testing-the-security-and-privacy-implications-ddb296093b6c)). Recall's 2024 plaintext-SQLite debacle and 2025 opt-in relaunch (BitLocker + Windows Hello, still leaking passwords in Aug 2025 tests) is the canonical privacy failure-mode study for any always-on personal index.

## 3. Vector index engineering for local-first NVMe

- **DiskANN** (NeurIPS 2019): billion vectors, one node, 64GB RAM + SSD, Vamana graph; ~5000 QPS, <3ms, 95% recall@1 ([MSR](https://www.microsoft.com/en-us/research/publication/diskann-fast-accurate-billion-point-nearest-neighbor-search-on-a-single-node/)). **FreshDiskANN** (arXiv:2105.09613) adds real-time insert/delete: in-memory buffer + background StreamingMerge; merge speed bounds sustainable update rate ([arXiv](https://arxiv.org/abs/2105.09613)). **SPANN** (NeurIPS 2021) is the cluster/inverted-list alternative, 2× faster to 90% recall at equal memory ([arXiv](https://arxiv.org/abs/2111.08566)); **SPFresh** (SOSP 2023) adds in-place updates. For "millions of files," this is comfortably over-engineered headroom — millions of vectors is the *easy* regime for these designs.
- **Practical embedded engines**: **LanceDB** (disk-native columnar Lance format, IVF-PQ larger-than-RAM, versioned writes — best batteries-included fit for NVMe); **usearch** (memory-mapped single-header HNSW, in-graph filtering, u40 IDs; you build the storage/update layer — a natural fit for a Zig CLI via its C API); **sqlite-vec** (SQL-native, simplest deployment, weakest top-end ANN) ([comparison](https://shaharia.com/blog/choosing-embeddable-vector-database-go-application/), [firecrawl guide](https://www.firecrawl.dev/blog/best-vector-databases)). ChromaDB has reported HNSW corruption on abrupt exit ([ADR](https://glama.ai/mcp/servers/@camilojourney/codesight/blob/7a2e5e7f7ebc6c10653253bd035e9e16e4de11c4/docs/decisions/0001-lancedb-over-chromadb.md)) — relevant to a durable-store design. Academic on-device work: **MicroNN** (Apple, arXiv:2504.05573) — disk-resident updatable vector DB with incremental updates at <2% of full-rebuild I/O.
- **Local embedding models (2025-26)**: **Qwen3-Embedding** family (0.6B at 639MB is the best sub-1GB model; 8B is #1 multilingual MTEB, Apache-2.0), **EmbeddingGemma-300M** (Matryoshka 768→128 dims — directly useful for shrinking on-NVMe indexes), **nomic-embed-text** (safe default, most-pulled on Ollama) ([bentoml guide](https://www.bentoml.com/blog/a-guide-to-open-source-embedding-models), [ollama comparison](https://www.morphllm.com/ollama-embedding-models); the [M5-Max Apple-Silicon benchmark](https://contracollective.com/blog/local-embeddings-apple-silicon-nomic-bge-qwen3-m5-max-2026) is a blog source — UNVERIFIED numbers).

## 4. Dynamic/online organization

- **SOM / streaming clustering**: active but niche. [Survey of recent SOM advances (arXiv:2501.08416)](https://arxiv.org/pdf/2501.08416); **SOTXTSTREAM** for density-based self-organizing text-stream clustering ([PMC](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC5501566/)); online k-means/BSAS/SOM compared head-to-head in a 2024 streaming-clustering paper ([arXiv:2405.03298](https://arxiv.org/pdf/2405.03298)). Growing SOMs handle "topology grows with your corpus."
- **Online convex optimization**: no paper frames *file organization* as OCO (genuine gap = opportunity). The nearest rigorous machinery is **dueling bandits / preference-based online learning** — learning from "A preferred to B" implicit feedback with regret guarantees, incl. **Dueling Convex Optimization** (Saha, Koren & Mansour, ICML 2021: ε-optimal point of a strongly-convex f from noisy comparisons alone; [PMLR](http://proceedings.mlr.press/v139/saha21b/saha21b.pdf), [general preferences follow-up](https://arxiv.org/pdf/2210.02562)) and online ranker evaluation via interleaving ([multi-dueling bandits, CIKM 2016](https://dl.acm.org/doi/10.1145/2983323.2983659)). This is the mathematically honest version of "continuously optimized, ideally convex parameter space": convex surrogate losses over view-ranking parameters, updated from pairwise implicit feedback, with regret bounds.
- **RL for interface adaptation**: real but immature. RL-based UI adaptation frameworks exist ([EICS 2024](https://dl.acm.org/doi/10.1145/3660515.3661329)); a 2025 *Empirical Software Engineering* study compares reward models and concludes RLHF-for-UI is mostly still simulation-based ([Springer](https://link.springer.com/article/10.1007/s10664-025-10659-5)); per-user preference models as reward modifiers in human-in-the-loop RL ([review](https://www.themoonlight.io/en/review/integrating-human-feedback-into-a-reinforcement-learning-based-framework-for-adaptive-user-interfaces)); "From Correctness to Preference" frames personalized agentic RL where optimal behavior is user-dependent ([arXiv:2605.23382](https://arxiv.org/html/2605.23382)). Nothing published does RL specifically for *file* organization — second genuine gap.

## 5. Virtual view layers on macOS (present learned views without moving files)

- **FSKit** is Apple's user-space FS API, public since macOS 15.4 ([Apple docs](https://developer.apple.com/documentation/FSKit), [Eclectic Light overview](https://eclecticlight.co/2024/06/26/how-file-systems-can-change-in-sequoia-with-fskit/)). Both FUSE projects converged on it: **macFUSE 5.x** ships an FSKit backend (`-o backend=fskit`; limitations: mounts only under /Volumes, no notification API, I/O slower than kext; active releases through July 2026) ([macFUSE backends wiki](https://github.com/macfuse/macfuse/wiki/FUSE-Backends), [5.2.0 announcement](https://macfuse.github.io/2026/04/09/macfuse-5.2.0.html)); **FUSE-T** now offers NFS, SMB, and native FSKit backends on macOS 26+ ([fuse-t.org](https://www.fuse-t.org/), [FSKit issue #69](https://github.com/macos-fuse-t/fuse-t/issues/69)). Net: a kext-free learned-views mount is finally realistic in 2026, with known perf/feature caveats.
- **Spotlight extension points**: classic `.mdimporter` transducers (heavily sandboxed: read target file + temp dir only — [theevilbit deep-dive](https://theevilbit.github.io/posts/macos_persistence_spotlight_importers/)); the modern CSImportExtension path has reported bugs persisting *custom* attributes ([Apple forums](https://developer.apple.com/forums/thread/763391)). Critical constraint: **Spotlight is a metadata query cache, not a metadata store** — you cannot inject arbitrary learned metadata; it must originate from file content or xattrs ([CocoaDev](https://cocoadev.github.io/SpotlightAndTagging/)). Smart Folders = saved queries = free virtual views over whatever you can get indexed.
- **Non-FS alternative** (lowest risk): own view database + app/CLI-level virtual folders — exactly what LSFS, Indaleko, and every shipping tool actually do. For `zt`: learned views as first-class CLI objects (`zt view <name>` materializing symlink trees or JSON), with FSKit as a later optional projection.

## 6. Redundancy/similarity substrate

- **FastCDC** (USENIX ATC 2016) remains the default content-defined chunker: Gear hash + simplified judgment + cut-point skipping + normalized chunking ([USENIX](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia), [paper PDF](https://csyhua.github.io/csyhua/hua-atc2016.pdf)); Go implementations report ~1350 MB/s ([kalbasit/fastcdc](https://github.com/kalbasit/fastcdc)). Trivially portable to Zig.
- **Near-duplicate detection**: MinHash-LSH is the dominant scheme (shingles → signatures → banding), used for C4/The Pile/FineWeb corpus dedup ([Milvus explainer](https://milvus.io/blog/minhash-lsh-in-milvus-the-secret-weapon-for-fighting-duplicates-in-llm-training-data.md), [interactive tutorial](https://mbrenndoerfer.com/writing/minhash-algorithm-jaccard-similarity-lsh-deduplication)). SimHash is the lighter alternative; both are semantically blind ("automobile manufacturing" ≠ "car production"), which is where embedding-cosine (SemDeDup-style) complements them — **SemHash-LLM** (arXiv:2607.01601) explicitly bridges hash-space and embedding-space dedup.
- **Connection to the redundancy-of-what-you-store metric**: the layering is clean — FastCDC chunk-hash overlap = byte-level redundancy; MinHash Jaccard = surface-text redundancy; embedding cosine = semantic redundancy. Tracking all three over time per store gives a genuine multi-resolution "entropy of the user's corpus" signal. No published system does this for personal stores — third genuine gap.

## 7. Failure-mode literature (the most important section)

The PIM literature is brutally consistent and mostly *against* naive auto-organization:

- **Navigation beats search, robustly**: users prefer folder navigation even with excellent search; search takes ~3× longer, costs more working memory (dual-task studies), and fails more ([Bergman et al., Personal & Ubiquitous Computing 2013](https://link.springer.com/article/10.1007/s00779-012-0544-z)); folder navigation recruits the same brain structures as spatial navigation ([Sci. Reports 2015](https://www.nature.com/articles/srep14719)); improved desktop search engines did *not* change filing habits ([TOIS 2008](https://www.researchgate.net/publication/220515581_Improved_Search_Engines_and_Navigation_Preference_in_Personal_Information_Management)). One counter-trend: over-50s search 4× more than twenty-somethings ([ASIS&T 2019](https://asistdl.onlinelibrary.wiley.com/doi/abs/10.1002/pra2.29)).
- **Self-created structure is the memory**: people remember classifications they made themselves; manual organizing is what builds the internal map of the external store — automating it away can *hurt* retrieval while saving effort.
- **Tagging under-delivers**: given folders and tags, users choose folders and rarely apply >1 tag/item; even Gmail re-added folders ([tagging workload study](https://www.researchgate.net/publication/215520598_An_Empirical_Study_of_Tagging_for_Personal_Information_Organization_Performance_Workload_Memory_and_Consistency)).
- **Trust collapses after visible errors**: classic automation-trust results — one or two visible misclassifications destroy reliance even on demonstrably-superior automation, unless errors are explained ([Dzindolet et al., role of trust in automation reliance](https://www.sciencedirect.com/science/article/abs/pii/S1071581903000387); algorithm-aversion line of Dietvorst et al.).
- Corroborated by the 2026 agent-memory result above: agents' own organization erodes and doesn't improve answers ([arXiv:2607.26637](https://arxiv.org/abs/2607.26637)).

**Design implications for z3store**: never move real files without consent (virtual views only); make every learned grouping explainable and reversible; treat user corrections as first-class training signal (dueling-bandit feedback); preserve user-created structure as ground truth, and *augment* rather than replace it; expect and design for the first visible error.

## Feasible in 2026 (locally) vs. speculative

**Actually feasible now, on one machine + external NVMe:**
- Content + metadata indexing of millions of files; incremental embedding with Qwen3-Embedding-0.6B / EmbeddingGemma-300M on Apple Silicon; usearch/LanceDB/sqlite-vec handle millions of vectors with headroom (billion-scale is the solved regime).
- FastCDC + BLAKE3 chunk store, MinHash-LSH near-dup, embedding-cosine semantic-dup — a full three-level redundancy metric.
- Virtual views: CLI-level views and Spotlight smart-folder projection today; FSKit mount (via FUSE-T or direct FSKit) is now genuinely available, with documented rough edges.
- Preference learning as *ranking*: dueling-bandit-style updates from "user opened A not B" signals over view orderings — small, convex, on-device.

**Feasible but hard / research-grade:**
- Activity-context capture à la Indaleko (needs collectors per source; privacy design is the hard part, per Recall).
- Stable incremental clustering that doesn't churn view identity as the corpus evolves (streaming SOM/micro-cluster methods exist but stability-vs-plasticity for *user-facing* views is unsolved).
- LLM-generated view labels/summaries locally (fine with a 4-8B model, but latency/energy budget on every reindex is real).

**Speculative in 2026:**
- Full RL loop autonomously reorganizing a personal store: no published success; two published warnings (agent-memory erosion; trust-collapse literature). "Hidden-layer optimization" of an organization network end-to-end from sparse personal feedback is data-starved by construction — a single user generates thousands, not millions, of preference events.
- Replacing (rather than overlaying) the hierarchy: 35 years of failures say the hierarchy must remain the substrate and the escape hatch.
- Truly convex end-to-end objective: convexity is achievable for the *ranking/weighting* layer (dueling convex optimization), not for embedding or clustering; claim convexity only where it's real.

## Proposed 4-phase ladder for zt

**Phase 1 — Index (the sensory layer).** Zig scanner over the NVMe repos: metadata + xattrs + FastCDC chunk hashes (BLAKE3) into SQLite; embedding sidecar (Ollama/llama.cpp serving Qwen3-Embedding-0.6B or EmbeddingGemma-300M with Matryoshka truncation to 256d) writing into **usearch via its C API** (cleanest Zig fit; sqlite-vec as fallback for pure-SQL simplicity; LanceDB if versioned datasets outweigh the Rust dependency). FreshDiskANN-style pattern: in-memory delta index + periodic merge, driven by FSEvents/watcher. Exit criterion: full reindex of ~1M files and incremental update latency budgets measured.

**Phase 2 — Metrics (the redundancy/similarity observatory).** Three-level redundancy report per store: chunk-level dedup ratio (FastCDC), near-dup clusters (MinHash-LSH), semantic-dup clusters (embedding cosine, SemDeDup-style). Add temporal dimension: redundancy of what the user *adds* over time. This phase produces the objective signals any later learning needs, and is independently useful (`zt dedupe --report`, `zt entropy`). Exit criterion: metrics stable and cheap enough to run per-commit of the store.

**Phase 3 — Virtual views (present without moving).** Learned/queried views as first-class `zt` objects: saved semantic queries, cluster views (streaming micro-clusters with sticky labels), timeline views (the lifestream, cheaply). Projections, in order of risk: (a) materialized symlink trees + JSON for tooling; (b) Spotlight/smart-folder projection via xattrs (respecting that Spotlight caches, never stores, metadata); (c) FSKit read-only mount via FUSE-T or native FSKit extension. Hard rule from §7: views never mutate real paths; every view explains its membership predicate. Exit criterion: user retrieves real work through views without noticing staleness.

**Phase 4 — Learned organization loop (closed-loop, bounded).** Not autonomous reorganization. Instead: (a) log implicit feedback (opens, dwell, view corrections, pin/unpin) locally; (b) dueling-bandit / online-convex updates over *view ranking and clustering hyperparameters* (a small, near-convex parameter space with regret guarantees) — not over file placement; (c) optional local-LLM proposer that *suggests* view refinements batch-wise with mandatory review (LlamaFS's one good idea), evaluated against Workspace-Bench-style synthetic stores plus your own store as the live benchmark; (d) explicit trust budget: surface confidence, make every learned change one-command reversible. Exit criterion: measured retrieval-time improvement vs. Phase-3 static views on your own usage log — the only benchmark that matters for a personal store.
