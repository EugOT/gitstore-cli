# Prior-Art Sweep: One Working Directory, Twin Private/Public Repositories (z3store/zt)

Scope: continuous, deterministic derivation of a public subset repo from a private full repo, driven by a checkbox manifest, with linked histories and background dual push/pull/commit/merge, orchestrated by a Zig CLI over git+jj.

---

## Part 1 — Tool/Mechanism Evaluations

### 1. Google Copybara

**What it does.** Transforms and moves code between repositories via an origin/destination model with a Starlark config (`copy.bara.sky`). Built exactly for "maintaining a confidential repository and a public repository in sync" ([github.com/google/copybara](https://github.com/google/copybara)). One repo must be designated *authoritative* (source of truth); contributions are allowed from either side.

**Continuity & direction.** Continuous, primarily one-way per workflow, with a reverse workflow (`CHANGE_REQUEST` / `CHANGE_REQUEST_FROM_SOT` + `core.reverse(transforms)`) for importing public PRs back into the private side. Workflow modes: `SQUASH` (default — collapses origin commits into one destination commit) and `ITERATIVE` (rewrites each origin commit individually — needed if you want 1:1 linked histories). `reversible_check` validates that transformations round-trip (default `True` only in `CHANGE_REQUEST` mode). Some transforms (e.g. `core.move` with `overwrite`) are inherently non-reversible ([docs/reference.md](https://github.com/google/copybara/blob/master/docs/reference.md), [examples.md](https://github.com/google/copybara/blob/master/docs/examples.md)).

**Linkage / state.** Stateless by design: "it stores the state in the destination repository (as a label in the commit message)" — the `GitOrigin-RevId` / `PiperOrigin-RevId` trailer pattern. This is the canonical production example of commit-message-trailer linkage; Google publishes internal Piper changelist numbers in every exported TensorFlow/Bazel/Abseil commit ([example commit](https://github.com/bazelbuild/bazel/commit/81a77e69a3e3bb9308d8bd72facea1e40b3c7bcf), [HN discussion](https://news.ycombinator.com/item?id=14811937)). Note: this *deliberately leaks* the private revision identifier; Google accepts that because Piper CL numbers are opaque integers.

**Determinism.** State-tracked (label-based), not content-deterministic: two independent runs from scratch do not reproduce identical destination SHAs (committer identity/date are set at import time — UNVERIFIED in exact detail, but the label-based state model exists precisely because outputs are not re-derivable byte-for-byte).

**Known two-way hazard.** Dagster (production Copybara user, hub-and-spoke) reports: Copybara has no native two-way sync; they built loop-prevention with custom RevId labels, and "if a commit lands on master of one repo before outstanding changes of its partner have been synced… you can end up with unintended reversion of the outstanding changes" ([dagster.io blog](https://dagster.io/blog/monorepos-the-hub-and-spoke-model-and-copybara)).

**Maturity / embedding fit.** Very mature (Google-internal + OSS community). But it is a **JVM application (JDK 11, Bazel build)** — completely unsuitable for embedding in a Zig CLI. Its *design patterns* (origin/destination, reversible transform DSL, RevId trailers, SQUASH-vs-ITERATIVE, authoritative-repo rule) are the thing to steal, not the binary.

### 2. josh (Just One Single History)

**What it does.** A git HTTP/SSH proxy that serves *filtered virtual repos* derived from a real repo, using a restricted filter DSL (`:/subdir`, `:prefix=`, `:exclude[...]`, `::file`, composition, `:workspace=`) chosen specifically so "filters are reversible" — arbitrary scripting is excluded to guarantee round-trip ([josh-project.dev/docs/intro](https://josh-project.dev/docs/intro.html), [filter reference](https://josh-project.dev/docs/reference/filters.html)).

**Continuity & direction.** Fully continuous and **bidirectional**: incremental filtering with persistent caching runs "on every single push and fetch," and pushes to the filtered repo are unfiltered back into the real repo. This is the closest existing implementation of "derived twin history with round-trip."

**Determinism.** "Tree-modifying filters produce consistent, deterministic outputs given identical inputs" — filtered history is a pure function of (input history, filter), which is exactly the property z3store wants.

**Critical caveat — not a security boundary.** Maintainers rejected a naive ACL PR because filter restrictions "can be easily circumvented as soon as the workspace filter is used… workspaces allow arbitrary re-composition of paths exposed as a virtual repo" ([josh PR #493](https://github.com/josh-project/josh/pull/493)). josh limits *visibility/scope for convenience*; anyone who can reach the proxy with upstream credentials can request a different filter. For z3store this caveat mostly doesn't bite, because the public repo would be a *materialized push target*, not a live proxy view — but it rules out "just run josh-proxy publicly in front of the private repo."

**Maturity / fit.** Rust, active project ("Git at scale platform", [github.com/josh-project/josh](https://github.com/josh-project/josh)). Embeddable only as an external binary or via Rust FFI; a Zig CLI could shell out to `josh-filter` (its CLI mode, [discussion #1386](https://github.com/josh-project/josh/discussions/1386)). Its filter-DSL-for-reversibility idea maps directly onto a checkbox manifest (a manifest is a compose of `::file` filters).

### 3. git-filter-repo / splitsh-lite / git subtree

**git-filter-repo.** The standard history-rewrite tool, but explicitly one-shot: its docs assume "repository filtering is something one would do very rarely… a one-shot operation," it refuses to run on non-fresh clones, and output SHAs are not guaranteed stable across git/filter-repo versions ([README](https://github.com/newren/git-filter-repo/blob/a6a6a1b0/README.md), [man page](https://manpages.debian.org/testing/git-filter-repo/git-filter-repo.1.en.html)). Usable to *bootstrap* the public repo once (or perform nuclear redaction), not to run continuously. Also: it's Python — a dependency z3store's policies would reject at runtime.

**splitsh-lite.** Go reimplementation of `git subtree split`: continuously splits monorepo subdirectories into read-only standalone repos; **deterministic** ("both tools generate the same sha1s" as `git subtree split` ≥ git 2.8); operates on git objects directly, cached, fast; powers the Symfony/Drupal "[READ-ONLY] subtree split" component mirrors run on every push/tag in CI ([splitsh/lite](https://github.com/splitsh/lite), [subtreesplit.com](https://www.subtreesplit.com/), [Drupal issue](https://www.drupal.org/project/drupal_cms/issues/3482737)). Limitations for z3store: directory-prefix based only (no per-file checkbox), one-way (mirrors are read-only), and it preserves original commit messages/authors verbatim (message leakage is not addressed).

**git subtree.** `add`/`split`/`push`/`pull` give crude bidirectionality for a *subdirectory*, with `--rejoin` to make repeated splits incremental ([git-scm.com/docs/git-subtree](https://git-scm.com/docs/git-subtree)). Deterministic split SHAs (same as splitsh-lite). Not per-file, merges pollute history, and continuous automation is famously fragile. Prior-art value: the `--rejoin` merge-marker trick is a linkage scheme (recording the split head as a merge parent) worth knowing about.

**gitrim (fardream/gitrim) — key find.** A Go library/tool purpose-built for exactly the z3store problem: deterministic per-file filtering of commit DAGs. "It filters the tree contained in each commit and copies over author, committer, and commit message, with parents replaced by the newly created commits and GPG signatures omitted. As long as the filters don't change, the generated git history is deterministic and can be one-to-one mapped back to the original repo." Round-trip: "modifications made in the trimmed repo can be recreated by filtering the changes, rejecting any that don't pass the filter, and applying them back to the original repo with original commits added as parents." Filter format: restricted gitignore-style patterns (`**`, `*`, root-relative; **no negation**) ([github.com/fardream/gitrim](https://github.com/fardream/gitrim)). Maturity: small/young (~88 commits) — treat as a design reference implementation, not a dependency. This is the closest single prior-art match to the z3store spec.

### 4. git sparse-checkout + partial clone — why they do NOT solve this

Consensus is unambiguous: "Git does not have per-file or per-directory access control… The sparse checkout is a performance feature and nothing more" ([security.stackexchange answer](https://security.stackexchange.com/questions/268836/is-git-sparse-checkout-secure)). `--filter=blob:none` still transfers the full directory structure and all file *names* of HEAD; nothing stops a client from re-cloning without filters; the server may legally send more than requested. Sparse-checkout affects only which paths are materialized locally; full history remains fetchable ([git-scm.com/docs/git-sparse-checkout](https://git-scm.com/docs/git-sparse-checkout)). Server-side path ACLs remain an unaccepted proposal in forges (e.g. [gitea #15691](https://github.com/go-gitea/gitea/issues/15691)). **Conclusion:** publication filtering must produce a *physically separate object graph* — which is z3store's premise. Sparse-checkout is however relevant *internally*: jj's sparse patterns could present a "public-only view" working copy for preview.

### 5. gitattributes `export-ignore` and .gitignore layering

`export-ignore` affects **only `git archive`** output (tarballs, Composer dists, GitHub release zips): "files ignored by .gitignore are not touched by Git at all… export-ignore rules only exclude the files when an archive is created"; clones/forks always get everything ([git-scm.com/docs/git-archive](https://git-scm.com/docs/git-archive), [feeding.cloud.geek.nz](https://feeding.cloud.geek.nz/posts/excluding-files-from-git-archive/)). `.gitignore` layering keeps files out of tracking entirely (no history at all — not "private history + public subset"). Neither yields a public *repository* with history. **Prior-art value only:** the attributes syntax (`pattern export-ignore`) is a well-understood per-path annotation surface; z3store's manifest is semantically "export-ignore inverted, applied to derived commits instead of archives."

### 6. Jujutsu (jj) native mechanisms

- **`git.private-commits`**: a revset of commits jj "will refuse to push"; commits matching it stop being private once they exist on the remote; immutable commits are excluded; a private commit blocks pushing its descendants ([jj config docs](https://docs.jj-vcs.dev/latest/config/)). This is a *guard rail* (prevent leaking WIP commits wholesale), not a *derivation* mechanism — it can't publish a file-subset of a commit. Directly useful in z3store as a safety net: mark every private-side commit `private:` w.r.t. the public remote so raw `jj git push` to the public remote can never ship a private commit; only the deriver writes to the public remote.
- **Workspaces** (`jj workspace add`): multiple working copies attached to one repo — useful for materializing a second working directory, but both see the same commit set; no content filtering ([working-copy docs](https://docs.jj-vcs.dev/latest/working-copy/)).
- **Sparse patterns** (`jj sparse set --add/--remove`, [man page](https://man.archlinux.org/man/extra/jujutsu/jj-sparse-set.1.en), [sparse-v2 design](https://docs.jj-vcs.dev/latest/design/sparse-v2/)): per-workspace path subsets of the working copy — again local materialization, not publication filtering.
- **Hidden/abandoned commits**: hidden from log but retained in the local op store; irrelevant to remote publication.
- **Relevant plumbing**: jj snapshots the working copy on every command and treats the working copy as a commit — a z3store daemon can hook "every private commit → derive public commit" off jj's op log cheaply. `snapshot.auto-track` controls what enters snapshots at all.

**Conclusion:** jj gives excellent *orchestration primitives* (op log as change feed, `git.private-commits` as push guard, workspaces/sparse for preview), but nothing in jj derives a filtered twin history. UNVERIFIED: no jj roadmap item found for publication filtering.

### 7. Encrypted-subset approaches: git-crypt, transcrypt, SOPS

Model: publish **one** repo containing everything, with private files encrypted via clean/smudge filters.

- **git-crypt**: "does not encrypt file names, commit messages, symlink targets… does not hide when a file does or doesn't change, the length of a file, or the fact that two files are identical" (deterministic AES-CTR keyed per file, required for git's change detection) ([AGWA/git-crypt README](https://github.com/AGWA/git-crypt), [agwa.name](https://www.agwa.name/projects/git-crypt/)). No key rotation for history (old key holders can always read old history). Not suitable "if the metadata of your repository is also sensitive." Also: security depends on the repo being tamper-proof (attacker who can push can edit `.gitattributes` to disable encryption).
- **transcrypt**: same clean/smudge mechanism, bash + OpenSSL, per-file salts, adds `--rekey`; identical metadata-leak profile ([turtles review matrix](https://danielsomerfield.github.io/turtles/reviews/)).
- **SOPS**: encrypts *values* in YAML/JSON/ENV/INI (keys/structure remain plaintext) plus whole-file BINARY mode; KMS/age/PGP backends ([getsops/sops](https://github.com/getsops/sops)). It's a secrets tool, not a repo-subset tool.
- **Whole-repo encryption** (`git-remote-gcrypt`) hides everything but then there is no meaningful public repo.

**Verdict for z3store:** rejected as the primary mechanism. Leakage profile is fundamentally wrong for subset *publication*: file names/paths, file sizes, churn cadence, commit messages and count of private files are all public. Retroactive redaction is *worse* than plaintext (unticking a checkbox cannot un-publish ciphertext already in public history; key rotation doesn't protect history). Possible niche: hybrid "greyed checkbox" state — publish an encrypted placeholder for files you intend to open later (timestamped proof-of-existence) — but that's an optional feature, not the core.

### 8. How big orgs actually run private→public mirrors

- **Google Chrome / Chromium**: does **not** filter one repo. Public `chromium/src` is the source of truth for OSS code; private code lives in wholly separate repos (`chrome/src-internal.git` and finer-grained internal repos) stitched in at *checkout time* via conditional `DEPS` entries (`checkout_src_internal`), with autoroll bots bumping pinned hashes ([google_chrome_branded_builds.md](https://chromium.googlesource.com/chromium/src/+/112.0.5615.165/docs/google_chrome_branded_builds.md), [DEPS](https://chromium.googlesource.com/chromium/src/+/master/DEPS)). ChromeOS: public vs private repo *manifests* plus `private-overlays/` ([source layout](https://www.chromium.org/chromium-os/developer-library/reference/development/source-layout/)). Lesson: at directory granularity, **composition beats filtration** — the boundary never moves and redaction is trivial (a private repo simply isn't referenced). But it can't do per-file checkboxes inside one tree.
- **Google's Piper→GitHub exports** (TensorFlow etc.): Copybara ITERATIVE with `PiperOrigin-RevId` trailers, internal authoritative (see §1).
- **AOSP**: batch model — internal development branch is private; code is periodically *pushed* to the public release branch ("at the flagship device's initial launch, the source is opened"); external contributions are cherry-picked inward; as of 2025/2026, `aosp-main` is read-only and source drops land in Q2/Q4 ([release lifecycle](https://source.android.com/docs/setup/contribute/release-lifecycle), [codelines](https://source.android.com/setup/start/codelines)). Lesson: squash/batch publication destroys the 1:1 linked-chain property z3store wants; it's the low-effort end of the spectrum.
- **GitLab**: single codebase in `gitlab-org/gitlab` (proprietary confined to `ee/`); `gitlab-org/gitlab-foss` is a generated **read-only mirror "with all proprietary code removed."** The sync is the [merge-train](https://gitlab.com/gitlab-org/merge-train) tool: commits transported via `git format-patch` + `git am --3way` (plain merges conflicted too much), with a file-removal list maintained in `merge-train/bin/merge-train`, and CI "as-if-foss" jobs that delete `ee/` and run the full suite *before* merge to guarantee the public projection stays green ([pipelines doc](https://docs.gitlab.com/development/pipelines/), [single-codebase issue](https://gitlab.com/gitlab-org/release/framework/issues/114)). Lessons: (a) directory-prefix boundary (`ee/`) chosen deliberately — per-file scatter was deemed unmanageable at scale; (b) **validate the public projection in CI on every private change** — z3store should adopt this ("as-if-public" gate); (c) patch-based transport is their answer to twin-history merge divergence.
- **Warp** ([warpdotdev/repo-sync](https://github.com/warpdotdev/repo-sync)): reusable GitHub workflows for bidirectional private/public sync; private→public produces a *clean stripped snapshot* (not per-commit history); public→private cherry-picks commits as-is; symlinks unsupported. [gjtorikian/repository-sync](https://github.com/gjtorikian/repository-sync) squashes private commits "to avoid leaking information." [ansys-tools-repo-sync](https://github.com/ansys/ansys-tools-repo-sync) is the closest manifest-driven tool: deny-by-default, ASCII manifest of regex patterns for allowed files, run in CI. All are snapshot-grade, none maintain linked per-commit twin histories.

### 9. Verifiable linkage between the twin histories

- **Plaintext trailers** (`GitOrigin-RevId`, `PiperOrigin-RevId`, Gerrit `Change-Id`): proven at Google scale; machine-readable (GitLab even exposes trailers via API — [Commits API](https://docs.gitlab.com/api/commits/)); loop-prevention keys for two-way sync (Dagster's `Internal-RevId` pattern). Cost: publishes the private commit ID verbatim. A raw private SHA-1/SHA-256 in a public trailer is (a) an oracle — anyone who later obtains candidate private hashes can confirm linkage; (b) a correlation key across leaks. Google mitigates by using opaque CL integers, not git SHAs.
- **Salted/HMAC commitments**: standard hiding+binding commitment — `com = HMAC-SHA256(k, private_sha)` with random per-commit 256-bit `k` stored privately; publish `com` in the public commit trailer; reveal `k` only when proving provenance ([hashed commitments](https://www.pokutta.com/blog/hashed-commitments/)). HMAC avoids length-extension; unsalted `H(private_sha)` is brute-forceable because SHAs are enumerable once partially known ([HackerNoon on GitHub commit privacy](https://hackernoon.com/why-github-commits-arent-as-private-as-you-think)). No off-the-shelf git tool implements this trailer scheme — UNVERIFIED that any prior tool does; treat as a novel-but-trivial construction. A real-world commit-reveal-with-git-SHA scheme exists in validator/competition contexts (commit the SHA publicly, reveal repo later).
- **Signing + transparency log**: sigstore **gitsign** signs commits with ephemeral Fulcio certs and records each signing event in **Rekor**, an append-only Merkle-tree transparency log; offline mode embeds Rekor verification attributes in the commit ([docs.sigstore.dev/cosign/signing/gitsign](https://docs.sigstore.dev/cosign/signing/gitsign/), [Rekor overview](https://docs.sigstore.dev/logging/overview/)). Fits z3store as *anchoring*: sign public commits (proves publisher identity + gives an external timestamp that the linkage commitment existed at time T). Privacy caveat from sigstore docs: public Rekor exposes commit timing and identity email — for the private side use a private Rekor or don't log it.
- **Hash-malleability caveat**: July 2026 research shows one signed commit content can map to multiple valid "Verified" hashes; don't treat a signature alone as a unique content ID; canonicalize before trusting ([thehackernews.com summary](https://thehackernews.com/2026/07/github-verified-commits-can-be.html) — UNVERIFIED technical details, but the design consequence is cheap: bind commitments to tree hash + parent chain, not just the commit SHA).

### 10. Failure modes (cross-cutting)

- **Retroactive redaction (unticking a checkbox).** Once published, deletion requires public history rewrite, and GitHub's own docs enumerate the residual vectors: forks, PR diff views, "directly via their SHA-1 hashes in cached views," and every existing clone; full removal needs GitHub Support intervention (cache purge, PR dereference, server GC) ([removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)). Design consequence: unticking must be modeled as **two distinct operations** — "stop publishing from now on" (cheap, safe, default) vs "scrub history" (destructive: filter-repo rewrite of the public repo + force-push + forge support ticket + re-anchor the linkage chain from the rewrite point; all downstream clones break). The manifest schema must record which was requested and when.
- **Rename/move leakage.** Moving `secret.zig → public.zig` (or vice versa) creates edges where content crosses the boundary: git rename detection is heuristic (content similarity), so a public commit can betray that the "new" public file has a large identical-prefix history, or a private file's content can appear as the rename source in a public diff if derivation is done patch-wise. gitrim-style *tree* filtering (recompute each public tree from scratch through the filter, never via diffs/patches) eliminates the patch-level vector; the residual risk is semantic (the first public commit of a formerly-private file exposes its full content and its private-era commit message if messages are copied). Mitigation: on first-publication of any path, force a manifest-attributed boundary commit with a synthesized message.
- **Merge conflicts / twin divergence.** The Dagster warning (§1) and GitLab's abandonment of plain merges for `git am --3way` (§8) both show that letting *both* sides advance independently corrupts linked histories. Every prior system that works picks one authority: Copybara ("choose one repository to be authoritative"), josh (real repo is authoritative; filtered pushes are immediately unfiltered into it), gitrim (public changes are validated against the filter and re-parented onto private commits), AOSP (internal authoritative, external cherry-picked). z3store must make the private repo strictly authoritative: public-side commits are never merged directly — they are lifted (filter-checked, re-parented) into the private repo, and the public head is then re-derived. The public repo's reflected head is always a pure function of the private head + manifest.
- **Force-push policy.** The public history must be append-only (protected branch, no force push) *except* during an explicit scrub, because the linkage chain (trailers/commitments) is what makes the mirror auditable; silent force-pushes break every verifier and every clone. Symfony/Drupal splits and gitlab-foss all run read-only public mirrors for this reason. jj note: `jj git push` force-pushes by design when rewriting; the deriver must therefore be the only writer to the public remote, and `git.private-commits` should fence humans off it.
- **Manifest-in-private-repo bootstrap paradox.** The manifest itself is a private file whose *effects* are public. If the manifest (or its hash) is ever published, checkbox history leaks the existence/timing of private files. Keep the manifest unpublished; publish only a derived, salted commitment if auditability of "what rule produced this commit" is needed.
- **Sibling-name leakage.** Even without publishing a file, its *name* can leak if trees are copied wholesale — recall partial clone transfers sibling names (§4). Derivation must rebuild trees containing only ticked entries, never redact-in-place.

## Part 2 — Ranked candidate architectures for z3store

### Rank 1 — "gitrim model": native deterministic DAG filter, private-authoritative, commitment-linked

The z3store CLI implements (in Zig, over libgit2-style plumbing or `git hash-object/mktree/commit-tree` + jj op log) exactly the gitrim algorithm: for each new private commit, filter its tree through the manifest, synthesize a public commit with copied author/date and (sanitized) message, parents = images of private parents; skip commits whose filtered tree equals the parent's (empty-change elision, configurable). Deterministic: public history is a pure function of (private history, manifest history) — any machine with the private repo can regenerate and *verify* the public repo bit-for-bit (gitrim demonstrates this is achievable; josh proves the incremental-cache performance model).

- **Manifest**: `PUBLISH.md` in the private repo root — markdown checkbox list, one `- [x] path` / `- [ ] path` per tracked file (globs allowed as `- [x] src/**.zig` with gitrim's restricted semantics: no negation, order-independent → deterministic). Parsed into a canonical sorted allowlist; a sidecar `.z3store/publish.lock` (generated, committed privately) records the canonicalized set + manifest blob hash + derivation-algorithm version, so derivation is reproducible even if parsing rules evolve. Manifest changes are themselves private commits and take effect at exactly that commit — the checkbox history *is* the publication audit log.
- **Linkage**: each public commit carries trailers `Z3-Link: HMAC-SHA256(k_repo, private_commit_id)` and `Z3-Prev: <sha of previous public commit>` (explicit chain); `k_repo` (or per-commit `k_i` derived via HKDF from a repo key + private commit id) lives only in the private repo's config, never published. Optional: gitsign the public commits so Rekor anchors existence/time externally. Never publish raw private SHAs (avoid the PiperOrigin-RevId leak) and never publish the manifest.
- **Merge semantics**: private repo strictly authoritative. Private merges map to public merges of the parent images (deterministic since both parents have images; if one parent's image is elided, collapse to single-parent — gitrim leaves merges under-specified, so z3store must pin this rule). Public contributions (PRs on the public repo) are never merged publicly; `zt adopt` filters the incoming change against the manifest (reject any touch outside the allowlist), re-parents it onto the corresponding private commit, lands it privately, and the next derivation reproduces it publicly — the gitrim round-trip. jj integration: derive on op-log advance (background daemon or post-commit hook); `git.private-commits = <all>` on the public remote for humans; deriver is sole public writer; force-push forbidden except `zt scrub`.
- **Top 3 leak risks + mitigations**: (1) *Commit-message leakage* — private messages copied verbatim mention private files/customers; mitigate with a message policy: publish only the subject line by default, run a deny-regex screen, and support a `Public-Message:` trailer override in private commits. (2) *Untick ≠ unpublish* — content persists in forks/caches/SHA-addressed views; mitigate by making `zt untick` forward-only and loud, with a separate `zt scrub` that runs filter-repo on the public repo, force-pushes, files the forge-support step, and re-keys the linkage chain from the scrub point. (3) *Boundary-crossing renames/first publication* — full private file history semantics leak at first tick; mitigate by synthesizing the first-publication commit (fresh add, generated message, no copied private message) and refusing to translate rename edges across the boundary.

### Rank 2 — "Copybara-shape orchestrator": patch-based ITERATIVE mirror with as-if-public CI gate

If bit-deterministic re-derivation is dropped as a requirement, z3store can be a thin, stateful-via-trailers orchestrator in the Copybara/GitLab-merge-train mold: on each private commit, compute the diff restricted to ticked paths, transport it with `format-patch`/`am --3way` (GitLab's battle-tested choice) onto the public head, stamp `Z3-Origin: <opaque monotonically-increasing publication id>` (Copybara's stateless-label trick, using an opaque counter instead of the private SHA). Simpler to build than tree-synthesis and naturally incremental; recovery = find last `Z3-Origin` label in the public repo (no local state), exactly Copybara's model.

- **Manifest**: same `PUBLISH.md`, but compiled to a `pathspec` set applied to diffs rather than trees.
- **Linkage**: opaque publication-id trailer + a private-side table `publication_id ↔ private commit` (jj-side metadata or a private ref `refs/z3store/linkmap`); optional HMAC commitment as in Rank 1.
- **Merge semantics**: SQUASH mode per push-batch optionally offered (AOSP/Warp style) for users who want *no* private cadence leakage; ITERATIVE for 1:1 chains. Public→private via cherry-pick inward (AOSP model). Mandatory "as-if-public" gate (GitLab pattern): before accepting any private commit, materialize the would-be public tree (jj sparse workspace with manifest patterns) and build/test it, so the public mirror never breaks.
- **Top 3 leak risks + mitigations**: (1) *Patch-context leakage* — `am --3way` diffs carry context lines and index hashes; if the manifest and diff base ever disagree, private hunks can slip through; mitigate by regenerating each patch strictly from filtered trees, never from raw private diffs. (2) *Divergence corruption* — the documented Copybara two-way race (unintended reversion); mitigate with a single-writer lock on the public branch and refusing derivation while an unlifted public PR is pending. (3) *Cadence/metadata leakage* — 1:1 commits expose private work rhythm and author identities; mitigate with optional batch/squash publication windows and author rewriting maps.

### Rank 3 — "Composition instead of filtration": Chromium-style split trees with jj workspace assembly

Invert the problem: restructure so private material lives in `private/` subtrees (or a sibling repo) and the public root is *born public* — GitLab's `ee/`, Chrome's `src-internal`, ChromeOS private-overlays all converged here at scale. z3store's role shrinks to (a) enforcing the boundary (hooks reject private-path references from public code), (b) assembling the unified working directory via jj workspaces + sparse patterns or a DEPS-like `z3store.zon` pin file that stitches the private repo in at a pinned commit, (c) autoroll commits updating the pin (public side records only an opaque pin of the private repo — or an HMAC commitment rather than a raw hash, improving on Chrome's plaintext internal hash pinning, which chrome-internal can afford only because the host is access-controlled).

- **Manifest**: becomes a *placement* map, not a filter: `PUBLISH.md` checkboxes move files physically between `pub/` and `priv/` trees (`zt tick` = `jj` move commit in both). Deterministic trivially — there is no derivation.
- **Linkage**: the public repo needs no twin chain; the private repo's superproject pin (commit id of public + commit id of private) is the linkage, recorded privately; releases signed with gitsign/Rekor.
- **Merge semantics**: plain git/jj merges within each repo — the twin-history merge problem vanishes entirely (the strongest argument for this architecture). Cross-boundary moves are ordinary commits in two repos coordinated by zt.
- **Top 3 leak risks + mitigations**: (1) *Boundary rigidity* — ticking a file means physically moving it, breaking imports/paths; mitigate with tooling-managed re-export shims, but accept this poorly fits "checkbox per file" UX (the reason it's rank 3 despite being operationally the most proven). (2) *Reference leakage* — public build files referencing private paths (Chrome gates with `is_chrome_branded`; z3store needs an equivalent comptime/build-option gate and a verify-tier check). (3) *Pin leakage* — publishing raw private commit ids in any public pin file; mitigate by keeping the stitch file private-side only.

### Decision guidance

Rank 1 uniquely satisfies the stated spec (per-file checkboxes, deterministic linked chains, seamless background twinning) and has a working proof-of-concept in gitrim plus a performance existence proof in josh; its costs are implementation effort in Zig and the irreducible redaction/message-leak policies. Rank 2 is the pragmatic fallback with the most industrial precedent (Copybara, GitLab merge-train) if determinism is negotiable. Rank 3 is what every org that faced this at scale eventually chose — worth keeping as the documented "escape hatch" restructure if per-file twinning proves operationally hairy.
